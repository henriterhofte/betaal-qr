Zo controleer je dit zelf

Betaal-QR belooft dat je betaalgegevens dit apparaat niet verlaten, en dat de site gebouwd is uit de openbare broncode. Je hoeft dat niet op mijn woord te geloven. Hieronder staat hoe je het zelf nagaat, van eenvoudig (een paar klikken) tot grondig (zelf bouwen en vergelijken).

1Wat wordt beloofd

  • De QR-code wordt in je eigen browser gemaakt. Naam, IBAN, bedrag en omschrijving worden nergens heen gestuurd, ook niet naar betaal.terhofte.net.
  • Opgeslagen ontvangers staan alleen in de opslag van je eigen browser (localStorage). Er zijn geen cookies, geen statistieken en geen accounts.
  • De site laadt alleen zijn eigen bestanden: geen scripts, lettertypen of beelden van andere sites.
  • De broncode is openbaar (GitHub, EUPL-1.2) en klein: één pagina en een paar honderd regels JavaScript, plus drie ongewijzigde bibliotheken (zie 6).
  • Een foto van een factuur wordt ook alleen in je browser gelezen, met tekstherkenning (Tesseract) die van deze site komt.
  • Een factuur (PDF) die je opent, wordt alleen in je browser gelezen. Het bestand gaat nergens heen; de pagina mag ook dan geen verbindingen maken.

2Kijk zelf naar het netwerkverkeer

Dit kost een paar minuten en vraagt geen technische kennis.

  1. Open Betaal-QR en druk op F12 (Mac: Cmd+Option+I). Kies het tabblad Netwerk (Network) en laad de pagina opnieuw.
  2. Je ziet alleen bestanden van betaal.terhofte.net langskomen.
  3. Wis de lijst en vul een betaling in. Er komen geen nieuwe verzoeken bij, ook niet als de QR-code verschijnt of als je een ontvanger bewaart.
  4. Open een factuur (PDF). De eerste keer zie je de PDF-lezer (pdflezer.mjs en de bestanden van pdf.js en jsQR) van betaal.terhofte.net komen. Je factuur zelf zie je niet langskomen: die wordt niet verstuurd.
  5. Nog eenvoudiger: zet de wifi uit (of vliegtuigmodus aan) en maak een code. Na het eerste bezoek werkt alles gewoon.

3De browser dwingt het af

De pagina geeft je browser een Content-Security-Policy mee: een regel die bepaalt wat de pagina mag. In de app staat hij onder Wat deze pagina mag. Zo luidt hij:

default-src 'none'; script-src 'self'; style-src 'self'; img-src 'self' blob: data:; manifest-src 'self'; worker-src 'self'; connect-src 'none'; base-uri 'none'; form-action 'none'

Wat dat betekent:

  • connect-src 'none': de pagina mag geen enkele verbinding maken, ook niet met deze site zelf. Er is dus geen kanaal om iets te versturen.
  • form-action 'none': er kan geen formulier ergens heen gestuurd worden.
  • script-src 'self' en default-src 'none': alleen scripts van deze site, en verder niets wat niet uitdrukkelijk is toegestaan.
  • worker-src 'self': alleen de eigen service worker. Die bewaart de bestanden van de site voor offline gebruik en ziet geen formuliergegevens.

De beperking zit in de pagina zelf. Ook als er per ongeluk of met opzet code in zou zitten die iets wil versturen, houdt je browser dat tegen.

4De build narekenen: is de site gebouwd uit de broncode?

Onderaan de app staat gebouwd uit commit …: de commit waaruit de site is gebouwd. In sha256.json staat dezelfde commit, met van elk bestand de SHA-256 (een vingerafdruk van de inhoud).

De build doet bijna niets. Alle bestanden zijn precies gelijk aan die in de repository, op drie na:

  • in sw.js wordt de cachenaam betaalqr-dev vervangen door betaalqr-<commit>;
  • versie.js wordt gemaakt, met de commit en de commitdatum;
  • sha256.json wordt gemaakt.

De build is reproduceerbaar: dezelfde commit geeft byte voor byte dezelfde bestanden.

Voor wie de opdrachtregel kent

Nodig: Git en Python 3 (alleen de standaardbibliotheek).

git clone https://github.com/henriterhofte/betaal-qr
cd betaal-qr
python tools/controleer.py

Het script haalt sha256.json van de site en bouwt die commit zelf opnieuw. Het vergelijkt elk bestand met het manifest, downloadt daarna elk bestand van de site en controleert dat ook. Bij succes staat er: gelijk: wat op https://betaal.terhofte.net/ draait, is gebouwd uit commit …

Daarnaast draait er elke week een automatische controle die precies dit doet. Die faalt als de site afwijkt.

5De herkomst: is dit echt door GitHub gebouwd?

Bij elke uitrol legt GitHub Actions vast dat sha256.json is gebouwd uit deze repository en deze commit. Dat gebeurt met een attestatie (SLSA-herkomst, ondertekend via Sigstore).

Voor wie de opdrachtregel kent

Nodig: de GitHub CLI (gh).

curl -O https://betaal.terhofte.net/sha256.json
gh attestation verify sha256.json --repo henriterhofte/betaal-qr

Bij succes staat er welke workflow en welke commit het bestand hebben gebouwd.

7Wat dit niet dekt

  • Je browser, je besturingssysteem en je extensies vertrouw je. Een kwaadwillende browserextensie kan meekijken op elke pagina, ook op deze.
  • GitHub is de host en de bouwer. De attestatie en de weekcontrole maken misbruik zichtbaar, maar voorkomen niet dat er tussen twee controles iets anders wordt geleverd. Wie dat wil uitsluiten, opent de app uit een eigen build: python tools/bouw.py en dan python -m http.server -d _site.
  • De code is niet door anderen beoordeeld. Een gelijke vingerafdruk bewijst dat de site uit de broncode komt, niet dat de broncode goed is. Juist daarom is hij klein gehouden.
  • Workers. Het zware werk (PDF lezen, tekstherkenning) gebeurt in zogeheten workers: aparte achtergrondscripts van deze site. Voor workers geldt de Content-Security-Policy van de pagina niet; daar geldt alleen wat de server meestuurt, en GitHub Pages stuurt niets mee. Het gaat om de ongewijzigde bibliotheken hierboven (met vingerafdruk), die alleen hun eigen bestanden van deze site laden. Je ziet dat ook in het netwerkverkeer (punt 2): de foto of PDF zelf gaat nergens heen.
  • Delen op Android. Als je een PDF deelt naar de geïnstalleerde app, stuurt Android hem als "verzending" naar het adres /gedeeld. De service worker van Betaal-QR vangt die op je telefoon af; er gaat niets over het netwerk. Alleen als die service worker ontbreekt (bijvoorbeeld als je de sitegegevens hebt gewist maar het app-icoon nog staat), zou de PDF naar de server van GitHub gaan, die hem met een foutmelding weggooit. Open de app daarom één keer gewoon voordat je deelt. "Openen met" op een laptop heeft dit niet: daar komt het bestand rechtstreeks bij de app, zonder netwerk.
  • Herkenning is geen controle. Uit een valse factuur leest Betaal-QR net zo goed een IBAN als uit een echte. Daarom blijft de stap "Klopt deze betaling?" verplicht, met de herkomst van elk gegeven.
  • Een kwaadwillende kopie van deze site (de code is openbaar) zou een ander IBAN in de QR-code kunnen zetten dan op het scherm staat. Vergelijk daarom altijd in je bank-app het IBAN met de factuur, en let op de naam-nummercontrole. Dat geldt ook voor deze site.
  • Bewust weggelaten: links met vooraf ingevulde gegevens. Die zouden oplichters kunnen gebruiken ("betaal via deze link"). Daarnaast weigert de app te werken als hij in een andere site is ingebed (clickjacking).
  • Geen betaaldienst. Betaal-QR maakt alleen een plaatje van de gegevens die je invult. Je bank voert de betaling uit, nadat jij hem in de bank-app hebt bevestigd.
